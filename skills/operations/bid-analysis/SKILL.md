# 标书分析技能

本技能用于把一份招标文件或 RFP/RFQ/RFI，从“资料”拆解成**两个可执行文档**：

1. **应标清单**：回答“为了提交一份合规且尽量高分的投标文件，我们必须准备什么？”
2. **交付物清单**：回答“如果中标，合同期内我们必须交付、验收、支持和承担什么？”

这两个文档必须分开抽取、分开组织，不能混写。

---

## 1. 默认输出

完整执行本技能时，默认只输出两个 Markdown 文件：

| 输出文件 | 核心问题 | 内容边界 |
|---|---|---|
| `项目名_应标清单.md` | 提交投标文件前要准备什么 | 符合性评审、经济标、商务标、技术标、评分表响应、技术规格强制响应、视频 / 证明材料、原厂授权、报价材料、排除项、P0-P4 执行优先级 |
| `项目名_交付物清单.md` | 中标后要交付什么 | 系统、模型、数据、平台、云资源、接口、部署、文档、验收、付款、发票、售后、知识产权、源代码、数据安全、违约、合同冲突和澄清事项 |

如用户只问局部问题，可只输出其中一个文档或其中一章；如用户要求完整分析，必须进行两次独立抽取：先做应标清单，再做交付物清单。

---

## 2. 使用场景

当用户给出以下资料或问题时使用本技能：

- 招标文件、采购文件、RFP、RFQ、RFI、招标公告、投标人须知；
- 技术规格书、货物和服务需求、评分办法、合同模板、验收单模板；
- 招标答疑、澄清公告、补遗文件；
- 已整理的应标材料清单、交付物清单、评分表拆解；
- 需要判断“这份标书要分析哪些维度”“应标需要准备哪些材料”“怎么拆评分项”“中标后要交付什么”。

---

## 3. 强原则

### 3.1 原文优先

- **招标文件 / 答疑 / 补遗是事实来源**，方案推断必须和原文区分。
- 每个关键结论必须尽量标注来源位置，例如：章节名、页码、行号、表格名、条款号。
- 涉及金额、比例、日期、数量、分值、阈值、服务期、验收节点、违约金、税率、份数、案例数量、视频数量等数字，必须逐字复核，不得凭印象改写。
- 如果资料由 PDF/DOCX/PPTX/XLSX 转换为 Markdown，需提示转换可能导致表格、数字、页码、图片语义丢失，关键数字应回看原件。

### 3.2 硬要求先于软材料

抽取顺序必须是：

1. P0 否决 / 符合性风险；
2. 经济标报价风险；
3. 商务标和技术标直接计分材料；
4. 技术规格强制响应 / 星号条款；
5. 强支撑材料；
6. 可选增强材料。

不要先写方案故事线，再回头找废标项。符合性不通过时，技术方案再好也没有意义。

### 3.3 应标与交付严格分离

| 阶段 | 文档 | 关注点 |
|---|---|---|
| 应标准备 | 应标清单 | 是否能投、怎么得分、需要什么证明 / 视频 / 方案 / 报价 / 授权 / 盖章 |
| 中标交付 | 交付物清单 | 合同后要交付什么、什么时候交付、如何验收、付款与责任边界是什么 |

禁止混淆：

- 不得把“投标阶段加分材料”写进“中标后硬交付物”；
- 不得把“中标后验收交付物”误写成“评分表必备附件”；
- 不得把“内部讲标辅助材料”误列为评分表必备材料。

### 3.4 表格忠实原则

- 评分表有几项就拆几项，不得为了显得完整而扩写成更多评分项。
- 商务评分表只有 4 项时，应标清单就只列这 4 项为商务计分项；其他材料只能列入“强支撑”或“排除项”。
- 每个评分项都要判断：是否需要方案、视频、证明、截图、案例、原厂授权、原厂盖章、第三方报告、仓库链接。

### 3.5 风险状态

对每条要求标注状态：

- `满足`：已有明确材料或能力证明；
- `部分满足`：方向满足但证据、盖章、格式或细节不足；
- `缺口`：当前没有材料或能力不满足；
- `待确认`：原文不清、材料未给、供应商能力需确认；
- `不适用`：招标文件明确不要求或与本项目无关；
- `需澄清`：原文存在冲突、边界不清或数字矛盾。

## 4. 总工作流

### Step 0：定位资料与转换

确认资料包中是否包括：

- 招标公告 / 投标邀请书；
- 投标人须知及前附表；
- 货物和服务需求 / 技术规格书；
- 评标办法 / 评分表；
- 合同资料表、合同模板、服务订单、验收单；
- 答疑、澄清、补遗；
- 用户已有的产品能力材料、案例、证书、报价、视频、交付清单。

输出内部索引：`资料清单 + 缺失资料 + 是否需要转换 / OCR / 表格复核`。

### Step 1：建立原文结构图

优先定位以下关键词和章节：

- `投标邀请书`、`投标人须知`、`前附表`、`合格投标人`；
- `符合性评审`、`否决`、`无效投标`、`实质性响应`；
- `评标办法`、`评分表`、`经济标`、`商务标`、`技术标`；
- `最高限价`、`投标保证金`、`投标有效期`、`报价修正`、`税率`；
- `★`、`必须`、`承诺书`、`不得负偏离`、`原厂授权`、`原厂盖章`；
- `视频演示`、`案例证明`、`第三方认证`、`截图`、`仓库链接`；
- `交付`、`验收`、`初验`、`上线`、`终验`、`付款`、`发票`；
- `源代码`、`知识产权`、`保密`、`数据安全`、`违约`、`售后`。

后续所有表格应引用原文索引。

### Step 2：项目一页纸判断

提炼：

- 项目目标和建设性质；
- 采购范围和关键系统 / 服务；
- 业务场景；
- 交付周期；
- 预算 / 最高限价；
- 评标方法与分值结构；
- 招标人最可能关注的业务目标与评审关注点。

该内容可作为两个输出文档的共同开头摘要。

## 5. 文档一：应标清单

### 5.1 应标清单回答的问题

`项目名_应标清单.md` 只回答投标提交前的问题：

- 哪些事项不满足会废标？
- 报价如何得分，报价文件要怎么准备？
- 商务标每一分对应什么材料？
- 技术标每一分对应什么方案、视频、证明、截图、报告？
- 哪些技术规格虽不直接计分，但必须响应或承诺？
- 哪些材料看似有用，但不是评分表必备？
- P0-P4 应该如何排优先级？

### 5.2 推荐章节结构

应标清单必须采用以下 9 章结构：

```markdown
# 项目名 应标准备材料清单

## 0. 本清单范围
## 1. 符合性评审必备材料 / 条件
## 2. 经济标必备材料
## 3. 商务标评分必备材料
## 4. 技术标评分必备材料
## 5. 技术评分视频 / 附件命名建议
## 6. 技术规格强制响应材料
## 7. 不纳入本清单的材料
## 8. 执行优先级
```

### 5.3 符合性评审

逐条拆解“不满足即废标”的事项。常见维度：

| 维度 | 检查内容 |
|---|---|
| 保证金 | 金额、形式、账户、有效期、付款主体 |
| 授权签署 | 法定代表人证明、授权委托书、身份证明、公章、签字 |
| 投标有效期 | 天数、起算点、保证金有效期是否覆盖 |
| 主体资格 | 营业执照、法人资格、分支机构唯一授权 |
| 信用记录 | 信用中国失信 / 重大税收违法查询 |
| 行贿犯罪 | 裁判文书网，投标人及法定代表人 |
| 黑名单 | 招标人或集团限制 / 禁止交易名单 |
| 异常一致 | IP、报名、下载、递交、解密、付款银行账户异常一致 |
| 关联关系 | 单位负责人、控股、管理关系冲突 |
| 联合体 / 分包 | 是否接受联合体、是否允许转包分包 |
| 最高限价 | 含税 / 不含税口径、是否超过控制价 |
| 报价修正 | 漏项修正 + 计算错误纠正比例阈值 |
| 实质性响应 | 偏离表、星号条款、承诺书、强制技术要求 |

表格字段：

```markdown
| 序号 | 符合性项目 | 招标要求摘要 | 需准备 / 确认的材料（含具体数值） | 原文索引 |
```

### 5.4 经济标

识别：

- 经济标满分；
- 评审价格口径：含税 / 不含税；
- 基准价计算方式；
- 高于 / 低于基准价扣分规则；
- 小数处理；
- 漏项、算术错误、税率、币种、限价校验；
- 付款节点对报价策略和现金流的影响。

必备材料通常包括：报价一览表、分项报价表、不含税评审价格核算表、含税 / 不含税口径校验表、最高限价校验表、报价计算复核表。

### 5.5 商务标

逐项列出商务评分项，不要把非评分材料误列为计分项。表格字段：

```markdown
| 序号 | 评分项 | 分值 | 招标要求 | 必备材料 | 原文索引 |
```

常见材料：企业资质、产品备案、CS 等级、CNVD、CCRC、原厂证明、授权证明、案例证明、合同 / 验收证明。

### 5.6 技术标

逐项把技术评分转成“可准备材料”。表格字段：

```markdown
| 序号 | 评分项 | 分值 | 必须准备的材料 | 视频 / 证明要求 | 原文索引 |
```

每个技术评分项至少识别：

- 是否需要视频演示；
- 是否需要方案文字；
- 是否需要案例证明；
- 是否需要原厂授权 / 原厂盖章；
- 是否需要仓库链接 / 截图 / 第三方报告；
- 视频演示输入、流程和验收要点。

### 5.7 技术规格强制响应

评分表之外，单独识别技术规格中的硬要求，尤其是：

- `★` 条款；
- 承诺书；
- `必须`、`不得负偏离`、`需提供`；
- 源代码、知识产权、内容安全、数据安全、国产化、部署、接口、文档交付；
- 原厂授权、第三方认证、兼容性证明。

表格字段：

```markdown
| 类别 | 材料 | 要求 | 是否强制 / 否决风险 | 原文索引 |
```

### 5.8 排除项

必须列出“不纳入应标清单的材料”，防止团队误把辅助材料当作必备材料。例如：

- 行业案例引用；
- 答辩 PPT；
- 讲标稿；
- 3 分钟电梯稿；
- 常见问题答复口径；
- 评委追问清单；
- 产品白皮书；
- 客户推荐信；
- 内部报价测算表。

可说明：这些材料可作为内部辅助或方案论证，但不是评分表明确要求的必备材料，除非招标文件另有说明。

### 5.9 应标执行优先级

默认使用 P0-P4：

| 优先级 | 含义 | 典型事项 |
|---|---|---|
| P0 | 否决风险，必须先完成 | 保证金、授权、资格、信用查询、报价不超限价、星号条款响应 |
| P1 | 直接计分材料 | 商务证书、备案、技术评分视频、方案、案例、认证报告 |
| P2 | 强支撑材料 | 截图包、页码索引表、原厂授权、仓库链接、视频说明 |
| P3 | 技术规格强制响应 / 交付支撑 | 承诺书、部署手册、接口规范、标注规范、培训与售后方案 |
| P4 | 增强材料 / 内部辅助 | 讲标稿、答辩 PPT、行业案例、评委追问口径 |

## 6. 文档二：交付物清单

### 6.1 交付物清单回答的问题

`项目名_交付物清单.md` 只回答中标后的履约问题：

- 合同签订后要交付哪些系统、服务、数据、模型、资源、文档？
- 每项交付内容的时间、数量、规格、验收方式是什么？
- 付款、发票、验收单如何关联？
- 售后、运维、安全、知识产权、源代码责任边界是什么？
- 合同条款之间有哪些冲突或需澄清事项？

### 6.2 推荐章节结构

交付物清单必须采用以下结构：

```markdown
# 项目名 交付阶段交付物清单

## 0. 总体交付边界
## 1. 数据准备与训练交付物
## 2. 模型训练、适配、部署与接口交付物
## 3. 系统 / 平台能力交付物
## 4. 云资源与基础设施交付物
## 5. 合同交付、验收、付款与发票要求
## 6. 私有化部署、运维与售后支持
## 7. 源代码、知识产权与交付边界
## 8. 安全、合规与数据保护交付 / 责任要求
## 9. 违约、延期与需澄清事项
## 10. 交付阶段交付物总清单
## 11. 逐行准确性复核结论
```

非 AI / 软件项目可将第 1-4 章改名为对应行业的交付模块，但仍需保留：合同、验收、付款、售后、知识产权、安全、违约、澄清。

### 6.3 交付维度

| 维度 | 分析要求 |
|---|---|
| 交付边界 | 系统、模型、数据、平台、云资源、接口、文档、服务 |
| 数据交付 | 数据量、场景、打标、质量、交付时限、培训 |
| 模型交付 | 基座、训练、微调、部署、API、元数据、升级迭代 |
| 平台交付 | Agent 平台、MCP、网关、注册中心、RAG、记忆、安全、可观测 |
| 云资源 | 机器类型、数量、CPU、内存、存储、网络、租用 / 采购 |
| 部署 | 私有化、生产环境、国产化、信创、镜像、联调、上线验证 |
| 文档 | 部署手册、接口规范、API 文档、运维手册、培训材料、验收资料 |
| 验收 | 初验、上线、终验、验收单、资料齐全、签章份数 |
| 付款 | 节点、比例、工作日、税率、发票类目、收票付款关系 |
| 售后 | 服务期、响应时间、远程 / 现场支持、正式与非正式环境边界 |
| 知识产权 | 源代码范围、智能体应用权利、第三方依赖、反向工程限制 |
| 数据安全 | 甲乙方责任、最小必要、敏感数据、合规提示、网络风险告知 |
| 违约 | 逾期交付、逾期付款、违约金、解除条件、甲方配合义务 |

### 6.4 合同冲突与澄清

交付物清单必须单独列出合同 / 技术 / 付款 / 验收之间的冲突。例如：

- 交付周期 A 处写 15 个工作日，B 处写 5/6/12 个月；
- 付款条款写“终验（上线）”，但交货期区分上线和终验；
- 源代码条款说“明确约定交付的源代码”，但服务订单未列范围；
- “全套技术文档”未定义边界；
- “规划与扩展方向”是否属于一期硬交付不清。

## 7. 版本化输出要求

两个文档都应包含 YAML frontmatter 和正文版本记录。

Frontmatter 示例：

```yaml
---
type: "report"
tags: ["投标", "应标清单", "交付物", "版本管理"]
summary: "一句话说明本文件范围"
sources:
  - "raw/tendors/xxx.md"
version: "v1.0"
status: "current"
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
version_history:
  - version: "v1.0"
    date: "YYYY-MM-DD"
    change: "初版：从招标文件提炼应标/交付要求。"
---
```

正文也应包含版本记录表。

## 9. 质量检查清单
