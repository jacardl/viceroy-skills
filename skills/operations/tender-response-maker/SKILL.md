# Tender Response Maker Skill

用于把招标文件变成可执行的应标材料体系。核心目标不是泛泛总结标书，而是**按招标原文逐条定位、抽取、归类、给出材料清单和响应策略**，并形成可版本管理的投标文档。

## 触发场景

当用户提出以下需求时使用本技能：

- “分析这个招标文件 / 标书”
- “输出应标材料清单”
- “评分表中一定要提供哪些材料”
- “检查投标材料有没有遗漏 / 不准确”
- “按招标文件逐条响应”
- “做投标技术标 / 商务标 / 报价标准备”
- “根据评分表准备 Demo / 视频 / 证明材料”
- “做版本管理，更新投标文档”
- “提炼交付阶段交付物 / 验收内容 / 合同交付要求”
- “从标书中整理中标后要提供哪些系统、文档、服务、源代码、验收材料”

## 核心原则

1. **招标原文优先**：所有结论必须回到招标文件原文，尤其是章节、条款、评分表、前附表、技术规格书。
2. **先硬要求，后建议项**：区分“否决项 / 必须提交 / 直接计分 / 强支撑 / 建议准备 / 加分材料”。
3. **评分表逐条抽取**：评分表中的每一项都要转化为：评分项、分值、原文要求、必须准备材料、视频/证明、原文索引。
4. **有数值必须写数值**：例如保证金金额、最高限价、投标有效期、正副本数量、截止时间、分值、扣分规则、案例数量、证书等级、视频数量等。
5. **有位置必须给位置**：输出中应提供“第几章 / 第几节 / 条款号 / 表格序号 / 原文行号（如可得）”。
6. **不要混淆材料性质**：行业案例、答辩 PPT、讲标稿、产品白皮书通常不是评分表必备材料，除非招标文件明确要求。
7. **版本化输出**：所有项目文档都应在 frontmatter 和正文版本记录中维护版本，不依赖单独 README 管理。
8. **Obsidian 原生**：输出到 vault 时使用 Markdown、YAML frontmatter、wikilinks。路径以 vault 相对路径为准。
9. **投标材料与交付物分离**：应标准备材料、评分表材料、交付阶段交付物、合同验收材料是不同输出；用户要求“交付阶段”时，只提炼中标后需要提供 / 完成 / 配合 / 验收的内容，不混入评分视频、答辩材料或行业案例。

## 工作流

### Step 1. 定位招标文件

读取用户指定的招标文件，常见路径包括：

- `raw/tendors/...`
- `raw/media/Tendor/...`
- 用户当前选中的文件
- 用户以 `@文件路径` 引用的文件

若文件为 DOCX / PDF / PPTX / XLSX 等复杂格式，应优先使用 MarkItDown 转为同目录 `.md` 中间文件；但原始文件仍是唯一事实来源，不得覆盖原始文件。

### Step 2. 建立标书结构地图

先快速定位以下区域：

1. 投标邀请 / 招标公告；
2. 投标人须知前附表；
3. 投标人须知；
4. 采购需求 / 技术规格书；
5. 合同条款；
6. 投标文件格式；
7. 评标办法；
8. 符合性评审；
9. 经济标 / 报价评分；
10. 商务标评分；
11. 技术标评分；
12. 带 `★`、`必须`、`须提供`、`承诺书`、`视频演示`、`证书复印件`、`原厂授权` 等关键词的条款。

建议用搜索关键词：

```text
评标办法
符合性评审
经济标
商务标
技术标
评分项目
评价标准
分值
投标保证金
投标有效期
最高投标限价
视频演示
证明材料
证书复印件
原厂授权
承诺书
★
必须
须提供
不得
否决
```

### Step 3. 抽取“符合性评审 / 否决项”

符合性评审不一定计分，但通常是最高优先级。

输出格式：

| 序号 | 符合性项目 | 招标要求摘要 | 需准备 / 确认的材料（含具体数值） | 原文索引 |
|---|---|---|---|---|

要求：

- 如果有具体数值，必须写出具体数值。
- 如果涉及账户、金额、日期、份数、比例、阈值，必须完整摘出。
- 如果是资格限制，应写出需要的声明 / 查询截图 / 承诺书。
- 必须给原文索引，如：`第一章 投标邀请书 / 投标人须知前附表 序号12`、`第二章 投标人须知第14条`、`第六章 评标办法 符合性评审序号1`。

常见符合性材料：

- 投标保证金；
- 法定代表人授权；
- 投标有效期；
- 营业执照 / 法人资格；
- 信用中国查询；
- 中国裁判文书网查询；
- 非联合体承诺；
- 不转包 / 不分包承诺；
- 最高限价校验；
- 报价修正比例；
- 重要条款响应；
- 纸质 / 电子文件份数；
- 密封、签字、盖章、解密要求。

### Step 4. 抽取经济标材料

输出：

| 项目 | 招标规则 | 原文索引 |
|---|---|---|

以及：

| 材料 | 要求 | 原文索引 |
|---|---|---|

必须抽取：

- 报价满分；
- 是否含税 / 不含税；
- 基准价计算方式；
- 高于 / 低于基准价扣分规则；
- 最高限价；
- 报价货币；
- 报价包含范围；
- 分项报价要求；
- 报价修正规则。

### Step 5. 抽取商务标评分材料

严格按评分表，不要把其他章节的资质建议混入商务评分表。

输出：

| 序号 | 评分项 | 分值 | 招标要求原文摘要 | 必备材料 | 原文索引 |
|---|---|---:|---|---|---|

材料常见类型：

- 资质认证；
- 备案证明；
- 项目团队；
- 人员证书；
- 社保证明；
- 类似业绩；
- 合同首页、金额页、签章页；
- 原厂授权；
- 原厂盖章证明。

注意：如果评分表只有 4 项，就只列 4 项；其他材料放入“非评分表但可支撑材料”。

### Step 6. 抽取技术标评分材料

逐条处理技术评分表。

输出：

| 序号 | 评分项 | 分值 | 必须准备的材料 | 视频 / 证明要求 | 原文索引 |
|---|---|---:|---|---|---|

对每个技术评分项识别：

- 是否要求视频演示；
- 是否要求方案；
- 是否要求证明材料；
- 是否要求代码仓库 / 截图；
- 是否要求第三方认证；
- 是否要求原厂授权 / 原厂盖章；
- 是否有案例数量；
- 是否有功能点列表；
- 是否有分值拆分；
- 不提供视频是否扣分；
- 是否存在分值与文字冲突，需要标注“需澄清”。

若评分项要求视频，建议给出视频命名：

```text
T01_评分项名称_视频演示.mp4
T02_评分项名称_视频演示.mp4
```

### Step 7. 抽取技术规格强制响应材料

除评分表外，还要搜索技术规格书中的：

- `★`
- `承诺书`
- `必须`
- `须提供`
- `交付物`
- `文档交付`
- `源代码`
- `部署手册`
- `接口规范`
- `兼容`
- `不得负偏离`

输出：

| 类别 | 材料 | 要求 | 是否否决 / 强制 | 原文索引 |
|---|---|---|---|---|

特别注意：带 `★` 的条款若负偏离可能导致否决，必须单独列出。

### Step 8. 抽取交付阶段交付物（用户要求交付/验收时）

当用户要求“提炼交付阶段要提供的内容”“中标后交付物”“验收材料”“合同交付要求”时，必须从评分表分析切换到**交付物分析**。不要只看评分表，要重点读取：

- 需求一览表 / 采购需求；
- 技术规格书 / 技术要求；
- 带 `交付`、`部署`、`验收`、`上线`、`初验`、`终验`、`服务期` 的条款；
- 模型部署与集成交付要求；
- 云资源 / 资源清单；
- 合同资料表；
- 合同条款中的交付及验收、付款、发票、售后、数据保护、知识产权、保密；
- 服务订单；
- 验收单模板；
- 投标文件格式中的技术规格响应 / 偏离表。

交付物分析输出格式：

| 序号 | 交付内容 | 具体要求 / 数值 | 准确性检查 | 原文索引 |
|---|---|---|---|---|

必须覆盖的交付维度：

1. **总体交付边界**：项目目标、系统范围、业务场景、交付节点。
2. **数据准备与训练交付物**：数据规模、数据场景、标注、质量校验、交付时效、培训支持、模型升级方案。
3. **模型训练 / 适配 / 部署 / 接口交付物**：算力适配、训练环境、镜像打包、环境部署、上线验证、API、联调、部署手册、接口规范。
4. **平台能力交付物**：智能体平台、MCP、AI 网关、RAG、注册中心、长短期记忆、A2A/MCP 规范、可观测、安全、沙箱、Tool Hub、SDK/API。
5. **云资源 / 基础设施交付物**：资源清单、数量、CPU、内存、存储、IO、网络、租用/自建方式、可靠性指标。
6. **合同交付 / 验收 / 付款 / 发票**：初验、上线、终验、合同有效期、付款比例、发票税率、验收单、文件资料齐全确认。
7. **私有化部署 / 运维 / 售后支持**：部署环境、甲方配合、乙方技术支持、应急远程、现场支持、正式环境与测试环境边界。
8. **源代码 / 知识产权 / 交付边界**：明确约定交付的源代码、非交付代码边界、智能体应用权利、第三方 IP 保证。
9. **安全 / 合规 / 数据保护**：内容安全、三涉四涉、数据处理、风险提示、网络安全告知。
10. **需澄清事项**：合同内部矛盾、术语混用、交付范围不清、源代码范围不清、文档边界不清。

交付物分析规则：

- 必须逐条给原文索引。
- 必须提取所有具体数值，如 `1个月`、`5个月`、`6个月`、`12个月`、`2000条`、`15轮`、`16–32卡`、`30%/30%/30%/10%`、`6%`、`8T`、`RTO<10s` 等。
- 如果合同资料表与合同模板冲突，必须标注“需澄清”，并说明哪个条款通常优先。例如合同资料表写“如两者不一致，以合同资料表为准”。
- 不要混入投标评分视频、答辩 PPT、行业案例，除非用户同时要求应标材料。

建议交付物文档结构：

```markdown
# 项目名称 交付阶段交付物清单 vX.X

# 0. 总体交付边界
# 1. 数据准备与训练交付物
# 2. 模型训练、适配、部署与接口交付物
# 3. 平台能力交付物
# 4. 云资源与基础设施交付物
# 5. 合同交付、验收、付款与发票要求
# 6. 私有化部署、运维与售后支持
# 7. 源代码、知识产权与交付边界
# 8. 安全、合规与数据保护交付 / 责任要求
# 9. 违约、延期与需澄清事项
# 10. 交付阶段交付物总清单
# 11. 逐行准确性复核结论
```

### Step 9. 区分不纳入本清单的材料

单独列出“不属于评分表必备”的材料，防止团队误解。

常见排除项：

| 材料 | 原因 |
|---|---|
| 行业案例引用 | 方案论证材料，不是评分表必备 |
| 答辩 PPT | 除非招标要求述标，否则不是评分表材料 |
| 讲标稿 | 内部准备材料 |
| 产品白皮书 | 除非作为能力证明附件，否则非必备 |
| 客户推荐信 | 若评分表要求合同案例，则推荐信不能替代合同 |
| 内部报价测算表 | 内部材料，不提交 |

### Step 10. 生成执行优先级

建议按优先级输出：

- **P0：否决风险，必须先完成**
- **P1：直接计分材料**
- **P2：强支撑材料，防止得分争议**
- **P3：技术规格强制响应材料**
- **P4：答辩 / 方案增强材料**

### Step 11. 版本化写入项目目录

若用户要求写入文件：

1. 使用项目目录，例如：`Projects/项目_xxx/`；不要假设使用 `Reports/`。
2. 文件名建议：
   ```text
   应标准备材料清单_v1.0_YYYY-MM-DD.md
   应标材料响应矩阵_v1.0_YYYY-MM-DD.md
   技术评分视频清单_v1.0_YYYY-MM-DD.md
   ```
3. 文档 frontmatter 必须包含：

```yaml
---
type: "report"
tags: ["投标", "应标材料", "评分表", "版本管理"]
summary: "一句话摘要"
sources:
  - "raw/.../招标文件.md"
version: "v1.0"
status: "current"
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
version_history:
  - version: "v1.0"
    date: "YYYY-MM-DD"
    change: "初版：..."

```

4. 正文开头也写版本记录表：

```markdown
## 版本记录

| 版本 | 日期 | 状态 | 更新说明 |
|---|---:|---|---|
| v1.0 | YYYY-MM-DD | 当前版本 | ... |
```

## 常见错误

1. **把投标准备全量材料当成评分表必备材料**：应区分正式必备与建议准备。
2. **遗漏符合性评审**：符合性不计分，但可能直接否决。
3. **遗漏具体数值**：保证金、限价、有效期、份数、案例数量必须写明。
4. **不写原文索引**：没有索引会导致后续复核困难。
