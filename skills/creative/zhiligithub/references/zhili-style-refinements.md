## 改稿模式 4 类（按命中率排序）

### 1. 去中文标点（命中率 11/18 ≈ 61%）

**用户的标点策略**：让节奏更紧，不要装饰性的标点。

| 原稿 | 改后 | 说明 |
|------|------|------|
| 「赛道**：**Web 容器化**。**」 | 「赛道 Web 容器化**。**」 | 冒号 → 直接连写 |
| 「📌 数据来源**：**GitHub Trending」 | 「📌 数据来源 GitHub Trending」 | 冒号 → 空格 |
| 「**。**Web 内容始终需要一个本地外壳」 | 「**位置。**Web 内容始终需要一个本地外壳**。**」 | 中间断句的句号 + 末尾句号合并 |

**主 SKILL.md「精简规则」第 1 条已写**：「禁用标点：冒号`：`、破折号`——`、双引号`""`」。**但实际还要补**：
- 「赛道 X：Y」的「：」是装饰性的，**Y 后跟句子时**改用「Y，」或直接连写
- 数据来源 / 元信息行的「：」也是装饰性的，**应该用空格替代**
- 中间断句的小句号「位置。Web 内容」合并成一个整句

**预检脚本**：写完扫一遍 `：[：]` 和 `。，`（句号+逗号紧邻），命中要改。

### 2. 精简冗余词（命中率 6/18 ≈ 33%）

**用户的精简哲学**：**已经说过的概念不再说，已经写过的论据不再复述**。

| 原稿 | 改后 | 说明 |
|------|------|------|
| 「先说一个让普通用户**难以理解的悖论**。」 | 「先说一个让普通用户**忽略的点**。」 | "难以理解"是修饰，"悖论"是高概念。换"忽略的点"——直接 |
| 「**2025 年**我们日常用的工具，70% 都是网页」 | 「**现在**，我们日常用的工具，70% 都是网页」 | 时间锚点越具体越脆弱，**"现在"比"2025 年"更耐用** |
| 「**3.7 年**来，Pake 一直没换过这个哲学。54,900 颗星**不是黑马速度，是**用户需求长期没被满足的证据。」 | 「**3 年**来，Pake 一直没换过这个哲学。54,900 颗星**是**用户需求长期没被满足的证据。」 | 数字精度从 3.7 → 3（避免精确数字带来的过度承诺感）；「不是 X 是 Y」二元结构删掉中间项 |
| 「**具体到代码层面，**Pake 做的事情分四步。」 | 「Pake 做的事情分四步。」 | 「具体到代码层面」是过渡语，删 |
| 「这些 commit 看着零碎，累积起来是 3.7 年没人敢动的稳定性。」 | （整段删） | 这是「事实 + 升华」的尾句，升华部分被砍 |
| 「三条命令就能把 weekly.tw93.fun 这个博客打包成本地 App，带自定义图标、自定义窗口尺寸、隐藏标题栏。」 | （整段删） | 命令行块后面的解释段落，**事实已在代码块里，复述是冗余** |
| 「54,900 颗星，3.7 年坚守，一行命令，5MB 出货。」 | （整段删） | 收尾的排比四连，**这是「万能展望结尾」的反例**——直接砍 |

**预检脚本**：写完后 grep 下面这些词，命中要砍：
- 「**具体到**」「**总而言之**」「**一句话**」「**说白了**」（过渡语）
- 「**不是 X，是 Y**」二元结构（renwei 11 项已要求 0 处，但要注意「**不是 X，是 Y**」删掉中间项也是常见操作）
- 代码块/表格后的解释段落（**通常复述了前面的事实**）
- 段尾排比（「54,900 颗星，3.7 年坚守，一行命令，5MB 出货」）

### 3. 去掉 inline code 反引号（命中率 4/18 ≈ 22%）

**用户的判断**：「代码标识符在公众号文章里不需要被高亮成 inline code」。

| 原稿 | 改后 |
|------|------|
| ` `.dmg` / `.msi` / `.deb` ` | `.dmg / .msi / .deb` |
| `injectScript` `injectStyle` | `injectScript` `injectStyle` |
| `userAgent` | `userAgent` |

**判断标准**（用户改的时候心里在想什么）：
- 如果 inline code 在**句子中间**，且**没有歧义**，改成普通文字
- 如果 inline code 是**命令 / 路径 / 真实代码**，保留反引号（但 Pake 这个 case 里，连命令都没保留）
- 关键：**反引号 ≠ inline code block**。代码块（`<pre><code>`）永远保留反引号

**预检脚本**：grep `[^`]+` ` 里的 `[^\`]+\`` 这种单反引号包裹的中文/标识符。命中后判断：
- 是命令 / 路径？保留
- 是英文术语（如 .dmg / .msi / API 名）？去掉反引号
- 是变量名 / 函数名（如 userAgent）？去掉反引号

### 4. 微调措辞（命中率 5/18 ≈ 28%）

**用户的语感偏好**：「**最有讲头**」→「**有意思**」、「**押对了**」→「**押了**」。

| 原稿 | 改后 | 说明 |
|------|------|------|
| 「**最有讲头的部分**」 | 「**最有意思的部分**」 | 「最有讲头」是 zhiliGitHub 自己的造词；「有意思」更口语、更稳 |
| 「押对了**一条没人敢押的路**」 | 「押了**一条没人敢押的路**」 | 「押对了」是完成时，「押了」是进行时——进行时更有现场感 |
| 「坏处是**体积**。」 | 「坏处是**体积庞大**。」 | 单字「体积」太空，加形容词 |
| 「**结果就是 5MB 这个数字**，包比 Electron 小 20 倍」 | 「**结果打出来的包只有 5MB**，比 Electron 小 20 倍」 | 「结果就是 X 这个数字」是套话模式；「打出来的包只有」更具体 |
| 「**Pake 的 3.7 年历史就是**...」 | 「**Pake 的历史就是**...」 | 数字精度问题（见模式 2） |

**预检脚本**：grep 「**最 X 的**」开头短语：
- 「**最有讲头**」「**最具价值**」「**最具影响力**」 → 改成「有意思」「值得一看」「挺有意思」
- 「**结果是**」「**这意味着**」「**本质上**」 → 改成具体描述

## 总体观察

用户改稿的核心模式可以总结成一句：**「文章不靠装饰，靠节奏」**。

| 维度 | AI 倾向 | 用户偏好 |
|------|---------|---------|
| 标点 | 用 `：` `——` `""` 制造层次 | 全去掉，让节奏紧 |
| 数字 | 越精确越好（3.7、98.6%） | 模糊化（3、绝大多数） |
| inline code | 默认包裹 | 默认不包裹 |
| 过渡句 | 越多越显「逻辑清晰」 | 全砍，直接进 |
| 排比收尾 | 「X、X、X」 | 砍掉，留一句核心判断 |
| 二元结构 | 「不是 X 是 Y」 | 改成纯判断「Z 是 W」 |

**为什么**：公众号读者在手机上 60 秒扫一篇文章，**任何打断节奏的元素都是阅读阻力**。用户的改稿不是在追求「更好的表达」，是在追求「更短的路径」。

## 给 agent 的实操清单（pre-submit 第 8 步）

写完 HTML 后，按下面顺序扫一遍：

```
□ 中文冒号 `：` 还有吗？（应该 0）
□ 反引号 inline code 在中文/英文术语位置？（应该改成普通文字）
□ 段落首「具体到...」「总而言之」「说白了...」？（砍）
□ 「不是 X 是 Y」二元结构？（改写成单判断）
□ 代码块后有解释段？（检查是否复述，删掉）
□ 段尾「X、X、X」排比？（砍掉或改成单句）
□ 「最 X 的」「结果是」「这意味着」套话头？（改具体描述）
□ 数字「3.7」「98.6%」过于精确？（降到「3」「绝大多数」）
```

**失败兜底**：8 项里命中 ≥ 3 项 → 打回重写，不要尝试一边改一边扫——AI 改稿会越改越用力。
