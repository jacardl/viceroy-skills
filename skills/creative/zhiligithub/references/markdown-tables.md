# Markdown 表格在 zhiliGitHub 草稿里的处理（2026-06-04 实操）

## 现状

zhiliGitHub 写草稿的 markdown 流程在 practical-writing-workflow.md 里没有专门处理表格。

按 streambert-reference.html 的 CSS 模板（样式 A）渲染时，**没有为 `<table>` 元素定义样式**。这意味着：

1. **如果保留 markdown 表格语法** `| 列1 | 列2 |`，md_to_blocks 把它当成一段连续的 p 块，渲染成 `<p>| 列1 | 列2 | ... | 值1 | 值2 |</p>` —— 微信草稿箱里会显示一长串带 `|` 的"行内伪表"，**视觉上非常丑**
2. **如果手工转 HTML `<table>`**，需要 inline 一整套表格 CSS（border-collapse / padding / nth-child 配色），而样式 A 没有现成模板，**容易破坏整体风格**

## 解决方案：表格 → 散文化

把 markdown 表格里的数据**拆成自然叙事段落**，跟卡兹克"跟朋友聊天"风格天然契合。

### 实操模板

**Before**（markdown 表格）：
```markdown
| 场景 | 压前 | 压后 | 节省 |
|---|---|---|---|
| 代码搜索（100 results） | 17,765 | 1,408 | **92%** |
| SRE 事故调试 | 65,694 | 5,118 | **92%** |
| GitHub issue triage | 54,174 | 14,761 | 73% |
| 代码库探索 | 78,502 | 41,254 | 47% |
```

**After**（散文化）：
```markdown
最猛的两个场景是**代码搜索 92%** 和 **SRE 事故调试 92%** — 也就是说，原本一万多 token 的工具输出，**压完只剩一千出头**。第三猛的 GitHub issue triage 是 73%，代码库探索是 47% — 后者边际收益小一些，因为代码库本身的「上下文信号密度」就比日志和搜索结果高。
```

### 为什么这个方案对

1. **避开了渲染 bug** — 没有 `<table>` 就不会被丢进 p 块
2. **符合卡兹克 L2-3 风格检查**："不用 bullet point 罗列观点" / "不大量加粗" — 表格本质是结构化罗列
3. **保留数据密度** — 关键数字（92% / 73% / 47%）还在，只是从"网格"变"叙事"
4. **节奏更好** — 散文化自带呼吸感，不会有"眼睛在表格上来回跳"的疲劳
5. **配 CSS 不用动** — 完全在样式 A 已定义的 p/strong 范围内

### 散文化公式

把表格转叙事时，按这个顺序想：

1. **极值点先说** — "最猛的是 X，第二猛是 Y"（读者先拿到峰值）
2. **极值后接解释** — 为什么 X 比 Y 猛（如果想解释）
3. **剩下的按梯度铺** — "第三是 Z，第四是 W"（不要逐个都说，给读者节奏）
4. **数据精度保留** — 92% / 73% / 47% 这种具体数字别丢，但可以用破折号或括号串起来
5. **如果表格有 baseline / 准确度对比**，单独拎一个"准确度这一块"段落

### 什么时候还是用表格

- **草稿阶段是 markdown 表格**（在写第一稿时）— 先用 markdown 表格组织思路
- **转 HTML 前**（`md_to_blocks` 之前）— 手动散文化
- **真正需要保留表格的例外**：当数据有强结构（比如"4 个 benchmark 的 baseline vs 压缩后"且数字必须按行列对齐看），可以在 HTML 里手写 `<table>` 套极简 CSS（`border: 1px solid #ccc; border-collapse: collapse; padding: 4px 8px;`），但要测试渲染效果

## 跟其他 Skills 的关系

- **khazix-writer L2-3**（"避免不必要的小标题 / 不用 bullet point 罗列观点"）— 表格本质是结构化罗列，**跟这条规则撞**
- **zhiliGitHub 实用工作流**（practical-writing-workflow.md）— 没有覆盖这个 case，本 reference 是补充
- **样式 A 渲染**（streambert-reference.html）— 没定义 table CSS，保留 markdown 表格会渲染坏

## 翻车点（2026-06-04 实操）

第一次写 headroom 草稿时，按 GitHub README 风格用 markdown 表格列出 4 个 workload 的压缩数据。转 HTML 后 `md_to_blocks` 把整段表格塞进一个 p 标签（12210 字符里有一大段 "| 场景 | 压前 | 压后..."），**微信草稿箱预览会显示成一坨带 | 的脏行**。**修复**：手动散文化成 3-4 句叙事，关键数字（92% / 73% / 47%）保留加粗强调。
